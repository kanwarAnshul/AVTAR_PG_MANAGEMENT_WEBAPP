## The one decision that matters first

There are two different kinds of "update". You need both, and they are configured differently.

| Update type | Contains | How it ships | Store review? | Time to user |
| --- | --- | --- | --- | --- |
| **Binary build** | New native module, permission, SDK upgrade, icon/name, splash | `eas build` → Play Store / APK | Yes | Hours–days |
| **OTA update (EAS Update)** | JS/TS, styles, text, images, business logic, new screens using already-installed native modules | `eas update` | **No** | Minutes |

> **Do this before your first Play release:** install `expo-updates`. If you publish v1.0.0 without it, that binary can *never* receive OTA updates — every fix would need a store release, and users on the old binary would stay broken until they update.

## Phase 0 — Choose your distribution model (Day 1)

1. **Google Play Store** — public discovery, trust, auto-updates. Cost: **$25 one-time**. New *personal* accounts (created after 13 Nov 2023) must run a **closed test with 12 testers opted in continuously for 14 days** before they can apply for production access.
2. **Direct APK / website / WhatsApp** — no review, instant distribution, but manual installs and no auto-update.
3. **Organization Play account** — the 12-tester rule applies only to *personal* accounts. An organization account needs a **D-U-N-S number** and business details, but skips the 14-day gate.

**Recommendation:** Play Store for the public app + EAS Update for instant fixes. Keep the APK path (`npm run build:apk`) for demos and for clients who won't use Play.

## Phase 1 — Prepare the codebase (Day 1–2)

1. Install the OTA client:
   ```bash
   npx expo install expo-updates
   ```
2. Configure updates and runtime version:
   ```bash
   npx eas-cli@latest update:configure
   ```
   This adds to `app.json`:
   ```json
   "runtimeVersion": { "policy": "appVersion" },
   "updates": { "url": "https://u.expo.dev/6977cd50-5983-4973-9541-3201a713128f" }
   ```
   and adds `"channel"` to the `preview` / `production` profiles in `eas.json`.
3. Add channels explicitly and pin the version source in `eas.json`:
   ```json
   {
     "cli": { "version": ">= 12.0.0", "appVersionSource": "local" },
     "build": {
       "development": { "developmentClient": true, "distribution": "internal" },
       "preview": {
         "distribution": "internal",
         "channel": "preview",
         "android": { "buildType": "apk" }
       },
       "production": {
         "channel": "production",
         "autoIncrement": true,
         "android": { "buildType": "app-bundle" }
       }
     }
   }
   ```
   - `appVersionSource: "local"` means `version` / `versionCode` come from `app.json`, so `runtimeVersion: appVersion` stays predictable.
4. Trim Android permissions in `app.json`. `RECORD_AUDIO`, `WRITE_EXTERNAL_STORAGE` and `READ_EXTERNAL_STORAGE` are not needed by this app and trigger extra Play policy scrutiny:
   ```json
   "android": {
     "blockedPermissions": [
       "android.permission.RECORD_AUDIO",
       "android.permission.WRITE_EXTERNAL_STORAGE"
     ]
   }
   ```
   (`expo-image-picker` already handles modern photo access via the system picker.)
5. Remove the debug-signing shortcut for release builds. EAS generates and stores a real upload keystore — do **not** ship `signingConfig signingConfigs.debug` from `android/app/build.gradle` (that file is generated by `expo prebuild` and is not committed).
6. Add a public privacy policy URL and link it from the app (Play rejects listings without one).
7. Add account deletion (required by Play for any app with sign-up):
   - In-app: **Profile → Delete my account** → Supabase RPC that deletes `auth.users` (cascades to `profiles`, `tenant_registrations`, `tenants`).
   - Web: a public page describing how to request deletion (can be the same URL as the privacy policy).
8. Optional but recommended: an in-app "update available" prompt using `expo-updates` (`checkForUpdateAsync` + `reloadAsync`), so critical fixes apply without a double restart.

## Phase 3 — Signing & credentials (Day 2)

1. Let EAS create the Android keystore:
   ```bash
   npx eas-cli@latest credentials --platform android
   ```
   Choose **Build credentials → Set up a new keystore**.
2. **Back up immediately:** download the `.jks` and store the keystore password + alias in a password manager. Losing it means you cannot ship updates to an existing Play listing (unless Play App Signing holds the app key).
3. Enrol in **Play App Signing** on first upload. Google holds the app-signing key; your keystore becomes the *upload* key and can be reset if lost.
4. Never commit keystores. `.gitignore` already blocks `*.jks`, `*.p8`, `*.p12`, `*.key`.

## Phase 5 — Store listing & compliance (Day 4–6)

1. **Store listing:** app name, short description (80 chars), full description (4000 chars), 2–8 phone screenshots, 1024×500 feature graphic, 512×512 icon.
2. **Privacy policy URL** — must be publicly reachable without login.
3. **Data safety form** — declare exactly what you collect:
   - Personal info: name, email, phone, address
   - Photos/videos: profile photo, Aadhaar/PAN images, complaint photos
   - App activity: complaints, presence, payments/dues
   - All encrypted in transit (HTTPS + Supabase), users can request deletion.
   > Aadhaar/PAN collection is sensitive. Keep the "collected for identity verification, encrypted at rest, not shared" wording consistent with your privacy policy and with `encrypt_pan()`.
4. **Content rating** questionnaire.
5. **Target audience** — 18+ (tenants are adults); do not target children.
6. **Ads** — declare "No ads".
7. **Test credentials for reviewers** — critical: the app is login-gated. Provide a working owner login and a tenant login in the "App access" section, plus steps to reach each portal.
8. **Account deletion** URL + in-app path (see Phase 1.7).

## Phase 6 — The day-to-day update workflow (ongoing)

### Ship a JS-only feature or fix (most releases)

```bash
# 1. verify
npx tsc --noEmit && npx expo lint

# 2. test on the preview channel
npx eas-cli@latest update --channel preview --environment preview --message "feat: dues reminder banner"

# 3. verify on a preview build, then promote to production
npx eas-cli@latest update --channel production --environment production --message "feat: dues reminder banner"
```

Users receive it on the next app start (updates download in the background, apply on restart — sometimes the second restart).

### Safe rollout and rollback

```bash
# gradual rollout to 10% of users
npx eas-cli@latest update --channel production --environment production --rollout-percentage 10 --message "..."

# change the percentage later
npx eas-cli@latest update:edit

# something broke — roll back to the previous update
npx eas-cli@latest update:rollback --channel production
```

### Ship a native change (new library, permission, SDK upgrade)

1. Bump `version` in `app.json` (e.g. `1.0.0` → `1.1.0`). This changes the **runtime version**, so old builds stop receiving the new updates — which is exactly what you want.
2. `npx expo install <package>`
3. `npx eas-cli@latest build --profile production --platform android`
4. `npx eas-cli@latest submit --platform android --profile production`
5. Publish the matching OTA update to `production`.

### Decision table — OTA or new build?

| Change | OTA? |
| --- | --- |
| Text, layout, colours, business rules | ✅ |
| New screen using existing modules | ✅ |
| Bug fix in API/Supabase calls | ✅ |
| Images, fonts, icons inside the app | ✅ |
| Add `expo-camera` / any native module | ❌ new build |
| Change permissions / AndroidManifest | ❌ new build |
| Upgrade Expo SDK or React Native | ❌ new build |
| Change app name, icon, splash, package id | ❌ new build |
| Change Supabase URL/key (env var) | ❌ new build (env vars are baked in) |

## Phase 7 — Release discipline (ongoing)

1. **Branches:** `main` = production, `develop` = preview channel. Publish OTA from the branch that matches the channel.
2. **Versioning:** `1.0.0` → patch `1.0.1` (JS-only release tag), minor `1.1.0` (new features + native change), major `2.0.0` (breaking/SDK upgrade).
3. **Scripts** to add to `package.json`:
   ```json
   "release:preview": "eas update --channel preview --environment preview --message",
   "release:prod": "eas update --channel production --environment production --message",
   "build:prod": "eas build --profile production --platform android --auto-submit"
   ```
4. **Optional CI:** `expo/expo-github-action` + a workflow that runs typecheck/lint on PRs and `eas update` on merge to `main`.
5. **Always republish from the same commit** you tested on staging (`eas update:republish --destination-channel production`).

## Phase 8 — Backend production checklist (before launch)

1. Migrations **005** and **006** applied (warden promotion, storage RLS, OTP, PAN encryption).
2. **Email confirmation OFF** in Supabase → Authentication → Providers → Email.
3. Real SMS provider configured + `pg_net` enabled + demo mode **off**:
   ```sql
   SELECT public.set_sms_provider('fast2sms', 'YOUR_KEY', 'AVTPG');
   SELECT public.set_sms_dev_mode(false);
   ```
4. DLT registration for Indian SMS senders (mandatory for transactional SMS).
5. Supabase **backups** — daily backups on paid plans; PITR if you can afford it.
6. `service_role` key is **never** in the app bundle (only the `sb_publishable_…` anon key).
7. RLS spot-check with a tenant account: cannot read other tenants, other properties, or `password_reset_otps`.
8. Staging Supabase project with the same migrations, wired through EAS environment variables.
9. Storage limits + file-size caps verified (5 MB buckets, 2 MB client cap).

---

## Phase 9 — After launch

1. **Crash visibility:** add Sentry (`@sentry/react-native`) — it is a native module, so add it *before* the first production build if you want it from day one.
2. **Update adoption:** EAS dashboard shows how many installs are on each update; expect a few days for full adoption.
3. **Play vitals:** watch ANR + crash rate weekly; a spike usually means a bad OTA → roll back.
4. **Quarterly:** upgrade Expo SDK one minor at a time, always as a new build.
